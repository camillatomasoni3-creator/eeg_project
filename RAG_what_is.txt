Retrieval-Augmented Generation (RAG) is a technique that enhances 
language model generation 
by incorportating external knowledge.

This is typically done by retrievaing relevant information from a large corpus of documents and using that information 
to inform the generation process.

Challenge:
- Clients often have vast proprietary documents
- Extracting specific information is like finding a needle in a haystack.

RAG is an approach in AI where LLMs are combined with external data sources 
to enhance the quality and accuracy of generated text.

Two steps:
- Retrieving relevant documents of information from external sources
- Augmenting the model's response with this up-to-date or specialized context 

Modern LLMs typically have a cut-off date for training data 
(e.g., ChatGPT’s publicly stated cutoff) and often lack 
real-time knowledge or deep domain expertise in certain areas. 

Moreover, they frequently provide references or citations that 
are incomplete or incorrect (“hallucinations”). RAG addresses 
these gaps by linking models to external, carefully curated 
sources like search engines(for real-time knowledge retrieval), 
vector stores(for relevant information retrieval), traditional 
databases(like SQL database) and many others.

Retrieval-Augmented Generation (RAG) expands the capabilities of a 
Large Language Model (LLM) by augmenting its knowledge with external data. 

The full RAG pipeline typically involves three major steps: 
Indexing, Retrieval, and Generation.

1. Intexing Phase:
- Source of Documents: collect and organize the documents 
or data sources we want the model to reference (PDFs, webpages, internal databases, ...)
- Chunking / Splitting: because most embedding models have limits 
on the amount of text they can process at once, each document is split into 
smaller pieces, known as chuncks.
- Decide on an Embedding Model: select an embedding model capable of converting 
text into numerical (vector) representations. 
- Indexing Embedded Chuncks in vector stores: 
    - Embedding: each text chunk is converted into numerical vector 
        that captures its semantic meaning
    - Vector Database (Vector store): these vectors are indexed and stored,
        allowing for efficient similarity searches.
    - In semantic space, chunks with similar content appear “closer” to each other.

2. Retrieval Phase:
- user question: a user submits a query (ex "What are the latest 
    updates in our company's leave policy?")
- embed the user query: using the same embedding model 
    employed during indexing, the system transforms 
    the user's query into a numerical vector
- perform similarity search: the embedded query is compared against the (already 
    embedded) vectors in the vector store to find the most relevant chunks.
    Technuques like cosine similarity or dot-product similarity or 
    similarity score threshold are typically used.
- retrieve relevant chunks: based on the similarity 
    algorithm used, relevant pieces of chunks from the 
    vector store are retrieved.
- context creation: the retrieved chunks are then combined into 
    a context package (text prompt) that will be passed to the LLM.
- optional query handling:
    - query translation
    - query routing: if multiple data sources or vector stores exist, the 
        system routes the query to the appropriate once

3. Generation Phase:
- Final prompt preparation: The user’s original query 
    and the formatted context(based on the retrieved 
    chunks) are integrated into a final prompt. This 
    prompt is then sent to the LLM for a response.
- LLM invocation: the LLM processes the prompt.
- output parsing: the LLM generates a response
- User-facing output: the final output is presented to the user, 
    reflecting up-to-date, context-relevant information.
